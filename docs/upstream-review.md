1. 先读本文件、当前维护说明及未关闭待办的详细计划。确认工作区、Git 规范和本站当前代码；不根据历史文档推定生产版本。

3. 验证旧边界是新终点的祖先，再枚举 `旧边界..新终点` 的所有可达提交，包括合并引入的提交。逐项阅读提交补丁，核对本站是否已独立修复、是否需要适配及是否与受保护定制冲突。
4. 同时复查本台账所有未关闭待办。新提交可能补充、替代或撤销旧方案；将关系写回原待办，不能只看新范围而丢失旧问题。
5. 每个新提交都记录结论：待实现、已在本站具备、暂缓或不采用；同一提交的不同部分可拆开登记。若仍有提交未检查，保留旧游标，并记录本轮未完成范围。
6. 全部新提交完成检查且结论落盘后，在同一文档 PR 中更新文件头、当前边界表、待办及历史记录。审核与实现可以分别提交；推进审核游标不需要等全部修复上线。
7. 之后的实现 PR 更新对应待办、本站提交和验证证据；合并与部署分别记录，不随意移动审核游标。

命令行网络可用时，可在仓库内获取远端对象并只读比较；下列操作不合并代码，也不修改远端配置：

```sh
git fetch --no-tags https://github.com/KKKKhazix/AIHOT.git refs/heads/main:refs/remotes/upstream/main
reviewed_sha=e57da5a4f151892a217529744cd68803aec580df
observed_sha=$(git rev-parse refs/remotes/upstream/main)
if ! git merge-base --is-ancestor "$reviewed_sha" "$observed_sha"; then
  echo '上游历史不可直接续接；先核对分支、对象完整性和历史变化'
  exit 1
fi
git log --reverse --topo-order --format='%H %s' "$reviewed_sha..$observed_sha"
git diff --stat "$reviewed_sha" "$observed_sha"
```

运行时从文件头复制当时的最新游标，不能永久使用示例中的值。空提交范围表示没有新提交，仍可继续处理台账待办。逐提交查看用 `git show <完整 SHA>`，不能只看最终文件差异；中间加入后又撤销的改动也要有审核结论。

网络受限时，可用 GitHub 只读接口先读取分支头，再按两个固定 SHA 调用 compare 和逐提交接口。必须确认响应没有截断或漏分页；API 失败、旧 SHA 不可达或历史被重写时，不根据日期猜测下一起点，也不推进游标。

目前采用一个固定 Markdown 台账加按日期保存的详细审查记录；文件头便于后续工具读取，无需另设一份容易失步的 JSON、Git tag 或自动同步任务。这里不新增 CI、定时检查、自动合并或自动部署。
