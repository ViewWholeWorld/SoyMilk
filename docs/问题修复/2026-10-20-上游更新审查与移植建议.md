## 建议近期移植的候选

### N1：请求输入与 HTTP 处理边界（高优先）

本站 `apps/api/src/http/respond.ts` 的 `strictQuery`／`looseQuery` 尚未包含上游的 NUL 拒绝；`apps/api/src/routes/og.ts` 仍用 `PAGES[name]`，可参考 `Object.hasOwn`；MCP 查询和 topic slug 也应统一拒绝控制字符，跳转对 slug 正确编码。site 路由需要将 `QueryError` 转为 400，不能只加入校验后让正常错误变成 500。

`packages/backend/src/lib/http-fetch.ts` 可参考用 `Headers.set` 合并请求头，避免大小写不同的 User-Agent 被拼成两个值；支持 `charset="gb2312"` 等带引号声明，并在文本解码后替换 NUL，保留原始 bytes 供图片或其它二进制消费者使用。此组修复无需扩大内网访问权限。

验收应覆盖 `%00`、重复参数、异常 OG 名称、编码后的 topic 路径、头部大小写及有引号字符集。HTTP API 行为变化还须在另一未迁移空库跑真实 HTTP 验收；本次没有据静态代码声称这些入口已被实际利用。

### N2：备份连接凭据不进入进程参数（高优先）

本站 `packages/backend/src/operations/backup.ts` 仍直接将 `config.databaseUrl` 传给 `pg_dump` argv。`execFile` 失败对象包含命令参数，因此存在通过进程参数或持久错误泄露连接凭据的风险；本次没有读取真实 URL、历史错误或生产日志确认泄露。

建议去掉 URL 用户名／密码及 query 中的 `user`／`password`，仅向该子进程传 `PGUSER`／`PGPASSWORD`，并校验失败序列化结果不含凭据。非凭据连接选项须保持 libpq 语义，尤其不能把 `+` 随意按表单空格重编码。保留本站现有对象存储凭据入口，不夹带上游改成仅环境变量的配置变化。

验收用虚构连接和可控子进程替身覆盖 URL userinfo、query 凭据、百分号编码、SSL／options、备份失败脱敏与原有归档流程。环境变量仍是凭据，不应进入日志或管理页。

### N3：翻译失败闭环与中文识别（高价值，需回执设计）

本站 `packages/backend/src/editorial/translate.ts` 将 `translation did not line up`、`no batch translated` 记为终态 skipped，可能使确定无效的译文不再恢复。但 `no batch translated` 也可能是首个段落超过 `MAX_CHARS`、`chosen` 为空，根本没有请求模型；必须按实际请求及结果区分无可翻译批次与付费响应不可用，前者保持跳过。当前中文判断也可能因汉字将日文／混合文本当作中文；建议共享语言判断，尊重明确的 `zh-*` 与非中文声明，未知语言再按 Han 且无假名／韩文等证据判断。

第 1 个提交引入的 `request_tag` 后来已撤销。最终上游通过 `rejectReceivedResponse` 将**确实收到但业务不可用**的响应标记为拒绝，在相同逻辑请求身份下有限重试；这和网络超时导致的 unknown 不同。本站批次接口尚无对应完整回执集合，需要先补齐回执 ID、消费者、批次对齐与落库事务，再实现这一行为，不能只把 skipped 改成 throw。

上游无效译文返回 `status: "failed"`；本站 `TranslateResult` 尚无该状态，`recordTranslationAttempt` 只在存在异常 `error` 时增加失败次数，并为异常设置五分钟后的 `retry_at`。仅新增 failed 返回值而沿用本站计数，会使已拒绝回执再次付费，却不累计失败次数。实施必须一起适配结果类型、`processTranslation`、失败计数／退避、`translatePending` 扫描及队列恢复；可使用明确的失败异常或显式失败结果，但两种入口的持久状态必须一致。保留同一文章版本最多三次真实失败的限制，等待和停机不计数，不能让上游调度器覆盖本站现有恢复路径。

本站 3.5.6 已有 `requestWait`／停机等待、分析轮次和迟到保护。unknown **在既有流程释放前**不能另发付费请求或切备用型号；源码中的 `operations/recover.ts` 已有超过 30 分钟自动放行一次的机制，由每 10 分钟调度的 `ops.recover` 执行，放行后沿原逻辑身份恢复，再次 unknown 留待人工处理。此处描述源码能力，不代表本轮查询或放行了生产回执；新增翻译恢复不能扩大或删除该机制。

验收至少覆盖：持续返回不可用译文时真实失败累计到三次便停止；五分钟退避有效；重启不清零；无请求的超长首段保持 skipped；预算／在途／unknown 等待不扣次数；有效 received 在业务落库失败后复用；旧轮次不能覆盖新输入。失败轮次限制不等于模型请求总数限制，一轮仍可能包含原批次、拆分和补译，须另记录请求数量及预算消耗。确定失败后的重试会增加费用，实施前应明确独立开关，不自动批量重翻历史，不调整账号、模型、强度或预算。

### N4：信源健康与告警证据（中高优先）

上游从固定“七天没内容”改为最多 90 天产出历史、至少 4 个产出日、中位间隔乘 4 的节奏判断；首次导入多条折算为一个产出日，同时统计发现入口。历史不足与从未收到内容分别解释，低频更新不再直接等同采集损坏。最终实现只为安静信源计算节奏，静默信息放周报，可修抓取问题按信源／问题报告。

建议适配 `sources/health.ts`、`operations/alerts.ts`、`operations/reports.ts`：后台展示节奏及证据，事故持续时长从首次检测起算，保留固定事故观察窗口；不能因文章自然老去或开关关闭就记恢复。可审计 dismiss 应在新故障证据出现时重开。额度拒绝按受影响型号和成功证据恢复，停止使用旧型号只降低影响程度，不伪造恢复。

本站飞书保持关闭，可先落后台诊断与纯计算，不为移植告警启用发送。验收使用低频源、首次导入、discoveries、日期边界、历史不足、持续积压、忽略后新证据等合成数据，关注查询范围与索引成本。

### N5：中英文搜索与相关度并列排序（中优先，读者收益直接）

本站 `packages/backend/src/publication/pool.ts` 的 `searchTerms` 主要按空格分词。上游将 `多模态RAG` 拆为 `多模态` 与 `rag`，保留 `10月` 等数字组合。词首限制只加在 `publicMatchCondition` 的正文分支，不能据此声称网页搜索也排除了 `rag` 对 `storage` 的命中。各入口应分别适配和验收：

| 入口 | 当前本站行为 | 固定上游可参考的变化与验收 |
| --- | --- | --- |
| 网页时间排序 | `directMatchCondition` 搜索主体／标题／摘要，不搜正文 | 使用新的中英分词；正文独有命中仍不能进入结果 |
| 网页相关度排序 | `partScore`／`anyMatch` 及 `splitFields` 分支按子串匹配正文 | 上游这里仍为子串匹配；适配分词和并列排序，分别验收单词优化分支、多词分支与筛选组合 |
| 公开 API／MCP | `publicMatchCondition` 允许主体／标题／摘要或许可正文命中 | 仅正文纯英文／数字词要求词首；查询 `rag` 时排除仅正文 `storage` 中部的命中，仍允许标题／摘要子串命中；不是完整单词匹配 |

相关度相等时优先有席位的精选，再按质量分、时间和 ID 稳定排序。本站与固定上游均为每页 40 条、最多 50 页，`total` 最多计到 2,000；相关度排序仍须考虑全部匹配候选，不能先截断候选再排序。建议保持六词上限、LIKE 转义、有界计数、分页一致性、许可与窗口筛选，并覆盖超过 2,000 个匹配项的验收。全量精确计数或统一各出口的正文词首匹配，均属于额外行为变更，须单独评估；SQL 改动要比较合成大数据上的查询计划。无需重新分析文章或调用模型。

### N6：日期解析与跨年展示（中优先，成本较低）

本站日期解析在 `packages/backend/src/sources/web-list.ts` 的 `parseLooseDate`，没有上游的 `sources/dates.ts`。可移植 `September 1, 2026 at 3:30 PM`、`Sep.` 等解析行为，并检查 AM／PM、非法日历日期、源时区偏移和不同进程 TZ。没有时区的源日期按既定源偏移处理，不依赖运行机器时区。

本站 `apps/web/app/features/feed/Timeline.tsx` 的 `DayHeader` 直接展示月日；上游跨年补年份值得采用。本站契约尚无上游新增 `monthDay` helper，须连同格式函数及使用点适配，覆盖北京时间年末／年初。同年保持简洁，异年显示年份；不改时间戳、排序或模型完成时间，不将该展示修复混同 A2 的数据库精度升级。

### N7：RSS、正文抽取与 SVG 说明（中优先，按小项拆分）

- RSS 相对链接应相对实际 feed 最终 URL 解析；Atom `updated` 不是首次 `published`。本站 `sources/rss.ts` 仍有 `published || updated` 回退，调整前需确认时间未知时的既有归档规则，不批量重写旧时间。
- `lib/text.ts` 仍用简单 `<[^>]+>` 去标签和少量实体表，遇属性值中的 `>` 或更多实体可能出错。上游使用 `entities`；实现时先检查可复用依赖，只加必要依赖，不顺带升级完整依赖树。
- `content/extract.ts`／`providers/jina.ts` 可借鉴 HTTP 200 错误页／验证码页识别，以及只在协议头读取 Jina warning 的策略。测试必须有正文正常讨论“404”的反例，不能仅凭关键词抹掉文章。已经收到的付费 Jina 响应保留回执，不能为抽取失败自动重新购买。
- SVG 四个连续补丁作为一个行为集处理：读来源文字说明，混合容器保留非 SVG 图片和正文，去重只看真正会保留的可见文字，排除隐藏／`aria-hidden`。说明按纯文字插入，不开放原始 SVG 执行。

本站 3.5.6 已将媒体／引用事实纳入输入版本，截图独立存储。采集后材料变化走正常版本保护；不自动给历史材料重新抽取／重分析，不擅自开启全文。真实材料差异复核应使用冻结脱敏样本，在隔离网络内进行。

### N8：额度拒绝冷却（中优先，必须按本站连接适配）

上游对 402 和带可靠供应商资金拒绝代码的部分 429，挂持久化 15 分钟冷却。普通 401／403 可能只是单资源权限，普通 429 可能是 RPM／TPM，不能都当整个服务额度用尽。终版键为 `provider.stop.${service}:${encodeURIComponent(model)}`，比前一提交 service 级更细。

本站动态连接可能共享 service/model，因此还应区分连接／供应商／账号和请求型号，不能让一个失败连接冻结其它有效连接。需测试旧在途成功不会清除较新拒绝、配置变化不会误用旧冷却、重启后仍有效和到期有限探测；这些是适配风险，非本轮已复现事故。保留现有 Codex `blockedUntil` 与订阅等待，不能借冷却自动换型号或新增付费请求身份。

### N9：反馈持久限流与幂等（中优先，有新迁移成本）

本站 `operations/feedback.ts` 目前主要用进程内分钟窗口。上游新增按来源锁定的持久状态、内容／邮箱／页面／截图指纹，相同提交短期复用反馈 ID；持续重放也计次数，临时封禁在到期读时失效、清理时审计，管理员解除同时清理窗口。这样可以减少重启、多 API 实例和丢失响应带来的重复提交。

可参考其事务和指纹设计，但不原样采用“每小时 3 条／20 次／封一小时”等产品门槛。邮箱未验证，只能作为显式人工处置的辅助标识，不能当可信身份或自动封禁依据；48 小时邮箱暂停也须单独确认策略。`clientIp` 只是抽取现有 `X-Real-IP` 逻辑，不等于修复了代理信任；验收必须核实入口确实覆盖该头，不能接受任意客户端伪造。

需新增本站自己的增量迁移和 HTTP 验收。保留 3.5.6 已修复的截图逐反馈独立存储、删除隔离、内容长度和安全检查；重复命中不多存文件，事务失败清理新文件，既有反馈不被自动封禁策略回写。

## 架构升级候选与代价

### A1：展示变化与语义变化分离，暂缓直接移植

上游新增 `content/presentation.ts`，在原文段落／内联结构可对应时，把更新后的图片和链接映射到既有翻译，避免全文重翻；不匹配抛出 `PresentationMismatch`，保留旧原文和译文，并将单条问题隔离。后台增加 `presentation` 重跑模式，先预览、提交版本哈希、事务内重新比对、按请求 ID 审计幂等，直接抓取失败不启动付费抽取后备。

这是较有价值的编辑和节费能力，但上游用 title/body/excerpt 判断内容身份的做法不能直接替换本站：视觉输入与引用事实变化即使文字相同，也可能改变模型判断。本站必须先定义完整模型输入哈希和纯展示指纹，仅对**已证明不影响任何付费输入**的变化复用译文与分析。验收至少覆盖图片替换、顺序变化、截图、引用、人工改文、并发采集、预览后远端变化与许可收紧。

### A2：发布时间证据精度与排序时间分离，中期设计

上游新增可空 `publication_time`，区分只有日期、完整 ISO 时间和未知；不把所有旧午夜时间猜成“只有日期”。归组提示词和页面可展示真实精度，排序锚点独立保存。未来发布时间最多提前 24 小时的声明到点再补采／排队，也有助于处理预发页面。

这会跨数据库、采集、契约、归组提示词、后台日期校正和公开页面。本站需自己的增量迁移（当前已有 `0050`），逐消费者适配，不复制上游 `0089` 或批量回填旧精度。人工日期校正还要保护正在处理的任务、人工归组和历史资料归档。按[时间轴规则](../内容管理/时间轴与时区.md)设计，并验证从不因模型完成时间改变时间轴。

### A3：采集详情恢复与公平轮转，中期设计

上游合并已知条目再补全，使用详情重试游标公平轮转、记忆已过期候选、复用已抓正文，预览与正式采集共用更多逻辑；截断响应只采纳可靠元数据，不保存截断正文，支持语言偏好及更完整代码／表格抽取。

应借鉴恢复和去重，保留本站七天窗口、首次每源 2 条、RSS 摘要展示与付费回执。不能把上游 admission 的较长窗口／首次数量带入本站。需用间歇失败、同 URL 多入口、无日期旧文、已抓正文、截断页和大量失败候选验证，明确持久游标与 revision 关系；收益是补全可靠性，成本是采集状态空间和旧游标兼容性。

### A4：事件阅读背景与当前关系证据，中期设计

上游保留 identity recall 14 天，将**已精选报道的阅读背景**扩至 60 天，按事实去重并排除已在身份候选中的事实。这不是“所有事件召回扩大到 60 天”。`latestJudgements`／`firmTie` 共享当前关系条件，避免链接生成和读取各用一套，`kept` 不被误当成新的关系判定。

上述“扩至 60 天”描述上游自己的基线。本站 `events/recall.ts` 没有 `recallSelectedBackground`，`events/relate.ts` 没有 `ReadingContext`／`SelectionValue`，`judgeBatch` 只返回关系判断；本站迁移定义中也没有上游的 `selection_adds_value`。上游阅读背景会进入模型的“新增阅读价值”判断，并由 `publication/publish.ts` 使用该字段影响能否入选。因此，对本站而言这是新增背景处理链及精选决策机制，不是简单修改召回天数。

A4 应拆成两项决策：当前关系证据的条件复用可独立评估；阅读背景是否参与精选则先确认内容策略。如果采用后者，另行设计提示词与版本、模型结果契约、增量字段及旧行语义、归组写入与公开投影、失败／人工覆盖和应用回退，不将该策略随关系查询优化自动带入。若只把背景用于辅助关系判断，也须写明与上游不同的行为及验收目标。

适配前要检查本站分析轮次、`output.stale` 过滤、roundup／composite 与关系结构。更长背景会增加数据库和模型输入成本，也可能让旧消息误压新进展；必须用五行业固定样本比较误合并／漏合并、精选误拒／误收、覆盖率和 token。撤回或许可受限报道不能留在阅读证据里；不能因模板复用丢掉当前输入版本校验。本轮仍暂缓实施，也未批准新的精选策略。

### A5：备份排空与迁移协调，独立运维方案

本站 `jobs/queue.ts` 的 `STOP_TIMEOUT_MS=195000`，基础 Compose `stop_grace_period=210s`。上游第 18 项初版 459 秒，最终 `4947ad0` 为队列 470 秒、Compose 515 秒；这些数字只说明上游给备份更多时间，不是本站可直接采用的参数。

上游迁移脚本增加 `waitForBackupDump`，识别当前数据库的 `application_name=pg_dump`，有界等待备份锁，不杀 dump，其它锁仍快速失败。可结合本站真实备份耗时设计停机窗口、进程信号顺序与锁分类，防止应用等得足够久却先被容器超时杀掉。NAS 基础 Compose 与迁移步骤需具体确认后实施，本轮未修改任何停机设置。

### A6：进行中查询去重，可随相关查询改动适配

上游 `lib/cache.ts` 抽出 `shared()`，只合并同时进行的读取，完成或失败后不缓存结果。可减少重复查询，但本站已有搜索合并与许可版本机制，不能当作全新缺失能力重复重构，也不能用它覆盖跨进程许可失效保护。

若采纳，键须包含完整查询与许可版本；有指定时钟的历史读取独立执行；拒绝 Promise 后可再次加载。许可收紧仍要同事务撤回投影并使所有公开出口立即失效，不能因上游异步 `requestRepublish` 而改成等 worker。长页面缓存仍是历史未批准方案。
