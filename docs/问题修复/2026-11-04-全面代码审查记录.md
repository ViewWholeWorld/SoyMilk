### 3.1 SEC-01：登录失败桶可被单 IP 灌满，锁死唯一管理员

**触发与影响。** `POST /api/auth/password` 在公开的 web 端口上可达。每次尝试都会先执行 `over("all", 50, now)`，把当前时间推进全局数组；单 IP 发 50 个任意密码请求即可在 15 分钟内填满全局桶。此后包括正确密码在内的所有登录都返回 `too-many`。攻击者每 15 分钟补发少量请求即可长期维持。被拒绝的请求仍然 `recent.push(now)`，数组随请求线性增长，每次请求完整过滤该数组，形成 O(n) 扫描与无界内存增长，可拖慢同一 API 进程的公开服务。重启 API 会清空内存桶，因此不是永久锁死，但唯一的恢复手段是重启。

**代码证据。** `apps/api/src/routes/admin-auth.ts:28-38`：

```ts
function over(key: string, limit: number, now: number): boolean {
  const recent = (attempts.get(key) ?? []).filter((t) => now - t < 15 * 60_000);
  recent.push(now);
  attempts.set(key, recent);
  return recent.length > limit;
}
function tooManyAttempts(ip: string): boolean {
  const now = Date.now();
  if (attempts.size > 5000) attempts.clear();
  const perClient = over(`ip:${ip}`, 10, now);
  return over("all", 50, now) || perClient;
}
```

`apps/api/src/routes/admin-auth.ts:94` 在密码比较之前调用 `tooManyAttempts(String(req.ip))`。

**建议与验收。** 改成固定窗口或令牌桶计数器：只对“真实失败”计数，已被限流拒绝的请求不再入桶；全局桶与单 IP 桶分离，全局桶的容量应远高于单 IP 的 10 次，或只在分布攻击特征出现时启用。限流表加容量上限与过期清理。验收覆盖：单 IP 连续 50 次错误后正确密码仍可登录（或至少全局桶不被单 IP 填满）；分布式多 IP 仍能触发全局保护；拒绝请求不增长数组；重启前后行为一致。

### 3.2 SEC-02：API 无条件信任代理头

`apps/api/src/app.ts:25` 设置 `trustProxy: true`。Fastify 会信任所有 `X-Forwarded-For` 跳数并取最左值作为 `req.ip`。当前部署中 API 不发布端口，web 在 `TRUST_PROXY=true` 时只把代理追加的最后一个地址传给 API，因此默认路径是安全的。但如果按注释把反向代理直接指向 API，或私有 compose 暴露了 3001，攻击者可以每次换一个伪造地址绕过登录 10 次/15 分钟与 ingest 10 次/分钟。反向配置错误同样有害：代理后漏设 `TRUST_PROXY=true` 时，所有访客在 API 看来是同一个代理地址，一次 10 次失败即锁住全部访客。

**建议。** API 的 `trustProxy` 改为由环境变量控制，或只信任 web 容器地址/CIDR；不把 3001 发布到非环回地址。验收覆盖：直连 API 伪造 XFF 不得改变 `req.ip`；经 web 代理时仍能拿到真实访客地址。

### 3.3 SEC-03/SEC-04：采集入口重放与鉴权前解析

`apps/api/src/routes/ingest.ts:9-18` 的 `INGEST_TOKEN` 是长期有效的静态 Bearer，没有时间戳、nonce 或 body HMAC，获得 token 的一方可以无限重放；`limited` 只按 `req.ip` 每分钟 10 次，`windows` Map 没有清理分支。`apps/api/src/app.ts:27` 的 `bodyLimit: 10 * 1024 * 1024` 是全局的，而 `authorized(req)` 在路由 handler 内执行，JSON 已在进入 handler 前完整解析。匿名请求可以向 `/api/admin/*` 与 `/api/ingest/items` 并发发送 10 MiB JSON，在鉴权或限流之前消耗内存与 CPU。

**建议。** 采集请求带短有效期时间戳 + nonce，或对 body 做 HMAC；限流改为 token + IP 的固定窗口并加全局配额；定期轮换 `INGEST_TOKEN`。为 admin/ingest 路由单独设置较小的 `bodyLimit`，或在 `preParsing`/`preValidation` 阶段完成鉴权。

### 3.4 SEC-05：HTTP 生产部署下的会话 Cookie

`apps/api/src/routes/admin-auth.ts:21` 的 `secure()` 只检查 `config.siteUrl` 是否以 `https://` 开头。AGENTS.md 明确生产可通过 HTTP 内网或 Tailscale IP 加端口访问，不要求 HTTPS，因此生产 Cookie 实际是 `HttpOnly; SameSite=Lax; Max-Age=2592000`，没有 `Secure`。同网段观察者可以抓取并重放该 Cookie 长达 30 天，登录密码也以明文提交。

**建议。** 若接受 HTTP 内网访问，至少把会话有效期缩短、增加空闲超时，并在文档中写明同网段威胁；若前面有 Caddy/Nginx，按 `X-Forwarded-Proto` 判定 HTTPS 并设置 `Secure`、HSTS 与 `__Host-` 前缀。为注销增加 CSRF token（当前只靠 SameSite=Lax）。

### 3.5 SEC-06：DEV_AUTH 不是 fail-closed

`packages/backend/src/config.ts:12` 的 `isProduction` 只认精确的 `NODE_ENV === "production"`；`assertProductionSecrets` 在 `!isProduction` 时直接 return。若生产进程以裸 `node apps/api/src/main.ts` 启动，或 `NODE_ENV` 写成 `Production`，`environmentName` 默认成为 `development`；此时 `.env` 中遗留 `DEV_AUTH_ROLE=admin` 会让任何不带有效 Cookie 的请求获得 `csrf: "dev"` 的完整管理员身份。仓库的 Dockerfile 与 compose 都设置了 `NODE_ENV=production`，受支持的启动方式不会触发，但保护应改为 fail-closed。

**建议。** 用显式 `AIHOT_ENVIRONMENT=production` 作为生产开关，或在生产构建/镜像中硬编码禁用 `DEV_AUTH_*`；启动时校验 `NODE_ENV` 大小写与 `AIHOT_ENVIRONMENT` 的一致性。

### 3.6 SEC-07/SEC-08/SEC-09：图片代理的三个边界

- **出口代理路径（SEC-07，疑似）。** `packages/backend/src/lib/http-fetch.ts:22-36` 在 `EGRESS_PROXY_URL` 存在且目标不是 IP、`.cn`、`.local` 时交给 `ProxyAgent`；`assertPublicUrl` 对代理路由只使用较窄的 `isInternalAddress`，真正解析与连接发生在代理侧。攻击者控制的域名可以对本地解析返回公网地址、对代理侧解析返回私网地址，形成 DNS 重绑定窗口。图片代理只接受签名 URL，攻击者需先让其 URL 进入被采集内容或通过 ingest 注入。需要在真实代理环境验证后再决定修复方式。
- **签名字段歧义（SEC-08）。** `packages/backend/src/media/imgproxy.ts:25-27` 用 `${url}|${mode}|${exp}` 直接拼接。URL 中的 `|` 会被 `new URL()` 保留；验证端用攻击者提供的 `u` 与 `mode` 重新拼接。若原签名 URL 的 `u` 含 `|`，可重切为不同的 `(u, mode)` 组合而签名不变。`u` 仍须是 http(s) 且过 SSRF 校验，`mode` 未知时回退 1600 宽，影响面窄。建议改用长度前缀或 JSON 编码的 canonical 串，或拒绝 `u`/`mode` 中的 `|`。
- **资源上限（SEC-09）。** `apps/api/src/routes/media.ts:28` 对每个不同的已签名 `(mode,url)` 启动最长 20 秒的抓取与 sharp 解码；`inflight` 只对相同键去重，没有全局并发或按客户端频率限制；磁盘缓存只写不删。`resizeImage` 未显式设置 `limitInputPixels`/`limitInputChannels`，使用 sharp 默认约 2.68 亿像素上限。建议设置显式像素/通道上限、全局并发信号量、磁盘 LRU/容量上限，并对图片代理加按 IP 的粗粒度限流。

### 3.7 OPS-01/OPS-02：备份与回退的运营边界

**备份静默（OPS-01）。** `packages/backend/src/operations/backup.ts:25-38` 的 `store()` 在 `DB_BACKUP_STORE_SECRET_ID/SECRET_KEY/BUCKET/REGION` 任一缺失时返回 null；`apps/worker/src/schedules.ts:63` 因此不注册 `ops.backup`，`operations/alerts.ts:272` 又跳过所有 `backup.*` 告警。新装或漏填一个变量时，系统可以长期零备份且后台“运行”页没有任何提示。建议：生产环境检测到部分备份配置时直接告警；未配置时也保留一条“未启用备份”的可见状态；定期做真实 restore 演练。

**回退不恢复数据库（OPS-02）。** `deploy/nas/auto-release.sh` 在检测到新增迁移时会先 `pg_dump` 并做 `pg_restore --list` 非空检查（第 261-264 行），但回退分支只恢复 `compose.release.yml` 并启动旧应用，不自动恢复数据库；脚本会打印“数据库已迁移，旧应用需兼容”。这是 AGENTS.md 已声明的策略（仅回退兼容应用，保留新状态），不是隐藏 bug。真正的缺口是：CI 只在空库跑全量迁移，不验证“上一版本数据 + 新迁移”的升级/回退兼容性。建议增加旧库升级测试与迁移兼容性门禁；不要在本轮把它写成未声明的缺陷。

### 3.8 OPS-03/OPS-04：迁移锁与迁移器

`database/migrations/0034_lz4_toast.sql:6` 的 `ALTER TABLE pool_search ALTER COLUMN body SET COMPRESSION lz4` 会触发表重写并持 ACCESS EXCLUSIVE；`0018_publication_sort_at.sql:13` 的 `SET NOT NULL` 全表扫描；`0049_model_stats_time.sql:3-4` 的 `DROP INDEX + CREATE INDEX` 不是 CONCURRENTLY。`scripts/migrate.ts:9-19` 把整个文件放在一个事务里，没有 `lock_timeout`/`statement_timeout`；自动发布此时已停止 API/web，停机时间等于重写/建索引时间。迁移器还没有 advisory lock、文件 checksum 或编号单调校验：并发迁移会在 `schema_migrations` 主键或 DDL 上失败；补一个低编号文件会让生产按“最后执行”应用、全新 CI 库按排序插入，造成 schema 分叉；改名会被当作新迁移重跑。

**建议。** `migrate.ts` 加 `pg_advisory_lock`、文件 checksum 与编号单调校验；大表 DDL 用 CONCURRENTLY/分批 SOP，并设置 `lock_timeout`；CI 增加“上一版本 schema + 数据样本 → 新迁移”的升级测试。

### 3.9 OPS-05/OPS-06：发布标签与 topics 覆盖

`deploy/nas/auto-release.sh:37-51` 在不带版本参数时从公开 tags API 取所有 `vX.Y.Z` 并按版本号最大者部署，不校验该 tag 是否位于 `main`、是否 CI 通过；显式传入低于当前运行版本的标签也会执行，且迁移差集为空时跳过数据库备份。任何有写权限者误推的高版本 tag 都会在 tag 工作流构建镜像后被自动选中。建议：部署前校验目标 tag 在 `main` 且 CI 成功，或用镜像 digest 固定；禁止无确认降级；目标版本低于当前版本时强制备份并显著警告。

### 3.10 OPS-07/OPS-08/OPS-09：Compose、数据库与连接池

- **共享密钥（OPS-07）。** `docker-compose.yml:5-20` 的 `x-app` 把 `env_file: .env`、`/data` 卷和 `DATABASE_URL` 注入 setup/api/worker/web。只负责 HTTP 代理与 SSR 的 web 容器因此持有 DB 凭据、`SESSION_SECRET`、`INGEST_TOKEN`、模型密钥，并对含 `model-config/connections.json`（明文模型 Key/Codex 授权）的 `/data` 有写权限；`ports: "${PORT:-3000}:3000"` 绑定 0.0.0.0。建议：web 只注入 `API_BASE_URL`/`SITE_URL` 等必要变量，`/data` 对 web 只读或使用独立卷；端口绑定 loopback/私网地址。

### 3.13 JOB-01/BUD-01/AUTH-02：任务恢复与付费分类

**JOB-01（P1）：未知回执放行后，归组/综述/预筛批次不会恢复。** `packages/backend/src/jobs/content.ts:302-306` 的 `ARTICLE_STEPS` 只覆盖 `prefilter/score/understand/summarize/structure`、`body_fallback`、`x_article`、`translate_body`；`receiptArticleSubject` 对其他 purpose 直接返回 null，`resumeAfterRelease` 因此不会把文章放回处理。`operations/recover.ts:32` 对每个 consumer subject 调用 `resumeAfterRelease`，但组、综述、预筛批次的 subject 不在白名单里。`jobs/queue.ts:128-140` 的 `retryReleasedReceiptJobs` 只重试 `output->>'receiptId'` 与放行审计匹配的 failed job，而 `events/group.ts` 的 `GroupResult`、`events/digest.ts` 的 `{updated, version}`、`jobs/prefilter.ts` 的 `{state}` 都不返回 `receiptId`。结果是：一个归组/综述/预筛批次回执因超时变成 unknown，30 分钟后被自动放行为 failed，但对应文章不会被重新归组、故事综述不再更新、预筛批次停留在 unknown；只有新活动或管理员重排才会恢复。建议把 receiptId 持久化到 job output 或专用 pending 表，按 purpose 恢复批次/事件/综述，并让 `resumeAfterRelease` 的白名单与 `retryReleasedReceiptJobs` 的匹配字段保持一致；补 group/digest/prefilter_batch 三类 unknown 的回归。

**BUD-01（P1）：Codex 的确定拒绝被当成 unknown。** `packages/backend/src/providers/receipts.ts:313` 只把 `ProviderRejectedError` 判为 `failed`，其余一律 `unknown`。`providers/codex.ts` 在用量上限/429/连接失败时抛 `CodexLimitError` 或普通 Error，于是明确未计费的额度拒绝也变成 unknown：文章被 `stopOnUnknownReceipt` 置 failed，30 分钟后自动放行并重发；`settleProviderCooldown(tx, cooldown, status === "unknown" ? "unknown" : "failure")` 不建立跨进程 provider cooldown，其他 worker/重启后的进程会继续打同一账号。建议区分“确定未发送/被拒绝”与“结果未知”：Codex 的 quota/rate/连接拒绝改为非付费失败或专用的 NotSentError，并把账号级 cooldown 写入共享状态。

**AUTH-02（P1）：ChatGPT 目录锁阻塞登录期付费调用，崩溃后永久残留。** `packages/backend/src/providers/chatgpt-auth.ts:69-87` 的 `withDirectoryLock` 最多等 35 秒，没有 mtime/pid 陈旧检测，`finally` 无条件 `rmdir`；`scripts/chatgpt-auth.ts:12-52` 的人工登录在最长 10 分钟的 OAuth 等待全程持锁。期间 worker 的 `chatGPTAccess` 每次等 35 秒后抛 “ChatGPT profile is locked”，被包装为 `ProviderUnavailable(configuration)`，队列转 300 秒等待，ChatGPT 通道实际暂停。若进程在刷新/登出时被 SIGKILL，锁目录不会像 Codex 的 privateLease 那样按 20 分钟租约回收，后续所有 ChatGPT 调用永久失败，直到人工删除；人工删除时旧进程的 `finally` 还可能删掉新持有者的锁。建议改为带 pid/mtime 的可回收租约，把“登录”和“刷新”分开加锁，并在 `rmdir` 前校验所有权。

**BUD-02 至 BUD-10（P2）概述。** 报告补生成没有失败次数上限，坏输出会每小时重复付费（`reports/compose.ts:250-253,352-388`、`schedules.ts:48`）；429/5xx 每次重试都是新付费 attempt 且不读 `Retry-After`（`receipts.ts:348-352`、`content.ts:215-224`）；管理端信源预览可绕过 `COLLECT_ENABLED` 触发 Jina 付费（`admin/sources.ts:80-88`、`providers/jina.ts:30-58`）；未决回执守卫按 `service` 过滤，未决期间切换供应商可重复付费（`receipts.ts:252-259`）；`budgets` 缺行等于无限额度（`receipts.ts:159`）；`completeReceipt` 无状态守卫，预筛可把 failed 回执改成 completed（`receipts.ts:427-429`、`jobs/prefilter.ts:181-207`）；失败/unknown 调用的 usage 丢失，token 统计系统性漏记（`receipts.ts:310-323`、`providers/codex.ts:228-239`）；分析并发代码默认 6，`ANALYZE_CONCURRENCY=2` 依赖部署环境（`jobs/content.ts:229`）；Codex 队列无单条等待上限，pg-boss analyze 600 秒过期可能重复执行（`providers/codex-session.ts:108-114`、`jobs/queue.ts:42`，疑似）。

### 3.14 COLL-01/COLL-02：Jina 轮次误删与采集放大

**COLL-01（P1）：busy/unknown 也会删除 Jina 列表轮次。** `packages/backend/src/sources/web-list.ts:354-373` 的 `fetchWebList` 在解析失败时删除 `sources.cursor.jinaListingRound`，注释说“An unusable rendering needs a fresh read”。但 catch 对任何错误都执行：定时采集与管理员“立即采集”使用不同 singletonKey，可以并发；第二个 run 复用 round A 后，`paidRequest` 发现回执 pending 抛 `ReceiptBusyError`，catch 删除 round A；60 秒后重试生成新 UUID，logical key 改变，于是再次向 Jina 付费。unknown 错误同样被清掉，原回执失去唯一关联。代码注释（`:154-156`）声称 unknown 会回到同一回执“避免再次付费”，实现与该不变量相反。建议：只在解析失败时清理轮次；busy/unknown/budget/关机必须保留；用 `SELECT ... FOR UPDATE` 或单条 `UPDATE ... RETURNING` 原子读取/创建 round；给 `collectSource` 加每信源 advisory lock。

**COLL-02（P1）：一次采集对候选与入库数量没有硬上限。** `packages/backend/src/sources/collect.ts:135-160` 在首次导入时把候选切到 30 条，但后续运行只做过滤、去重和可选的新闻窗口，没有条数上限；`store()`（`:68-79`）对每个候选逐条 `upsertMaterial` 并 `queueProcessing`。一个 8 MB 的 RSS/Atom 可以塞入数万条紧凑 `<item>`，网页列表同样可以产出数万链接；每条新文章还会入队正文抓取（每条最多 20 秒，可回落付费 Jina）。一次轮询即可产生数万 DB 事务、队列任务和外网请求，worker 长时间被占满。预算熔断只限制模型/Jina 金额，不限制 DB/队列/普通抓取放大。建议：给每 feed/列表最大条目数、每次运行最大入库数、每次运行最大详情/正文抓取数；超限按失败运行记录诊断，而不是继续入库和入队。

### 3.15 COLL-03 至 COLL-10：采集与内容边界

- **URL scheme（COLL-03）。** `sources/rss.ts:164-165` 用 `URL.parse(href, res.url)` 接受任意 scheme；`json-list.ts` 的 `{raw}` 模板同样可以产出 `javascript:`/`data:`；`allowed()` 在 `allowUrlPrefixes` 为空时返回 true，仓库 seed 的 RSS 信源均未配置该字段。`identityKeyFor` 对非 http(s) URL 回落到 `src:<sourceId>:<hash>`，因此仍会入库。公开 RSS 的“阅读原文”直接输出 `<a href="${escapeXml(r.url)}">`（`publication/feeds.ts:91`）；站点页面由 React 的 URL 清理兜底，但 RSS 阅读器与第三方 API 消费者不一定。建议在所有入口（RSS/Atom/JSON/ingest，以及 `itemUrlPrefixRewrite` 之后）再校验 http(s)，公开输出时兜底过滤。
- **日期归档（COLL-04）。** `sources/collect.ts:170-186` 在 `publishedAtAuthoritative` 为 true 时先把 `c.publishedAt = null`，然后才判断详情预算；预算耗尽或详情失败时，剩余候选以无日期入库，`decideTimeline` 视为“此刻发现”，旧文被当作今天并进入 live 时间轴。后续运行命中 `known` 分支会在预算判断前 `continue`，日期永久无法补齐。建议把清空动作移到“确认会执行详情抓取”之后，并为历史无日期文章保留一次补日期机会。
- **相对链接与时间（COLL-05/06）。** `sources/web-list.ts:166-170` 用配置 URL 而非 `res.url` 作 base；列表 302/301 到新路径或新主机时，相对链接会落到错误路径。`rss.ts:46-54`、`json-list.ts:58-59`、`ingest/items.ts:65` 对无时区时间直接用 `Date.parse`/`new Date`，在 Docker 默认 UTC 下会把中文源的 `10:00` 解析成北京时间 18:00；网页列表已用 `parseLooseDate(..., utcOffset)` 规避，其他入口未复用。建议统一时间语义，base 改用最终 URL。
- **媒体与解析（COLL-07/10）。** `media/images.ts` 未显式设置 sharp 的 `limitInputPixels`/`limitInputChannels`，默认约 2.68 亿像素；一张 16383×16383 的 PNG 解码 RGBA 约 1.07 GB，动画路径 `ANIMATION_MAX_PIXELS = 200_000_000` 峰值约 800 MB。`content/sanitize.ts:59,75-78` 允许 `data:` 图片和 `<video src>`，但 `proxyBodyImages` 只改写 `<img src>` 与 `<video poster>`，公开页读者会直连第三方地址。建议设置显式像素/通道上限、媒体处理并发上限，并让 `video src` 与 `data:` 媒体走签名代理或剥离。

### 3.16 PUB-01/PUB-02/PUB-07：公开出口的三处边界

**PUB-01（P1）：隔离信源的名称仍进入公开统计与热点聚合。** `packages/backend/src/site/stats.ts:24,31,34` 的 sources 计数、`sourceKinds` 和 `sampleSources` 都只按 `enabled`/`kind` 过滤，没有排除 `participation_mode = 'isolated'`；`apps/web/app/features/about/SignalRiver.tsx:509` 会把 `sampleSources` 作为真实信源渲染并显示名称。`packages/backend/src/publication/hot.ts:29-33,62-67` 复用 `hot_rankings` 里的 `sourceNames`/`participants`，而 `queryExtras` 的头像查询同样未过滤 isolated；若信源在隔离前已进入 ranking，下一轮 5 分钟重算前仍会显示。泄漏的是信源身份与数量，不是文章内容。建议：所有公开 sources/信号聚合统一加 `participation_mode <> 'isolated'`，并加一条“设为 isolated 后 about/hot/stats 不出现该名称”的回归。

**PUB-02（P2）：发布闸门被详情页、Markdown、availability 与分享图绕过。** `packages/backend/src/publication/rules.ts:43-45` 的 `hasItemPage` 只检查 `visibility !== 'withdrawn'` 与 `sourceMode === 'editorial'`，不检查 `releasedCondition(now)`；`publication/detail.ts:54`、`publication/availability.ts:15-16`、`publication/og.ts:14` 都复用它。精选文章写入 `visible_after = now + 180s` 后，列表、v1 items、snapshot 和 RSS 都隐藏，但只要知道 article id，`/api/site/items/:id`、`/api/site/items/:id/original`、`/items/:id/markdown`、`/og/items/:id.png` 仍返回标题、摘要甚至全文，availability 还会报 `public`。id 在闸门前不进入公开列表，利用前提是 id 已从其他渠道获得；这是读取规则不一致，不是大规模泄漏。建议在 `scope.ts` 增加统一的“公开详情页”谓词（visibility + editorial + `releasedCondition(now)`），让四个入口共用，并加“闸门内 id 直接访问应为 404”的测试。

**PUB-07（P2）：DB 恢复后公开缓存可能无限循环。** `packages/backend/src/publication/cache.ts:18-35` 的 `epoch` 是进程内存值，只在 `current > epoch` 时上升；`readPublicationCache` 在 `before < epoch` 时 `continue`。如果进程存活期间数据库被恢复到旧快照、`publication.permission-epoch` 行被删除或重置为较小值，`currentEpoch()` 返回小于内存 `epoch` 的值，循环永远不会退出，所有走公开缓存的请求会挂起并持续打 DB。建议检测到回退时重置内存 `epoch` 并清缓存，或给循环加有限重试与告警。这个触发需要“DB 恢复且进程未重启”，概率低，但后果是公开读取不可用。

**PUB-03 至 PUB-09（P2/P3）概述。** 分组展开/事件进展的 offset 来自游标但未校验类型与范围，畸形游标可让 `slice` 返回整段（`publication/groups.ts:47-57`）；timeline 的 `tag` 过滤键无界且 `queryGroupedAnchors` 无 LIMIT，轮换随机 tag 可穿透 50 条缓存并放大为全精选扫描（`publication/timeline.ts:76-110`）；MCP 的 `parsedBody` 路径绕过 SDK 的 256KB 限制，实际由 Fastify 10MB 兜底（`apps/api/src/routes/mcp.ts:262`）；OG 渲染无全局并发/速率/磁盘上限，sitemap 可枚举约 45k id（`apps/api/src/og/render.ts:116-141`）；`tip` 过滤包含 `opinion` 但返回 `category` 仍为 `opinion`（`publication/items.ts:85-89`）；agent 的 304 未列 OpenAPI，报告 navigation 对不存在的 key 返回 200（`apps/api/src/routes/agent.ts`、`publication/reports.ts:445-449`）。

### 3.17 JOB-02 至 JOB-12：事件合并、报告补生成与归组恢复

**JOB-02（P1）：事件合并的事务边界不完整。** `packages/backend/src/events/merge.ts:13-35` 在一个事务里移动 facts、story_signals，设置 `merged_into`，写 alias；事务提交后才逐篇 `publishArticle(a.article_id)`，然后才入队 digest。如果 worker 在循环中崩溃、被部署停止，或某次 `publishArticle` 抛错，部分 `publications.story_id` 仍指向旧故事。时间轴按 `publications.story_id` 分卡，`stories` 又过滤 `merged_into`，于是同一事件会以“旧卡片 + 新卡片”两个组出现，旧组没有故事链接。更麻烦的是重试无效：`mergeStoryInto` 看到 `merged_into` 非空直接返回 null，管理员接口随后抛 `Conflict("两个事件都必须是未合并的事件")`；没有重投影/清扫任务修复这些 publications。建议把重投影与 digest 入队做成可重入任务，或以 facts/fact_articles 实时判定故事归属，不依赖 `publications.story_id` 的物化副本。

**JOB-03 至 JOB-12（P2/P3）概述。** 报告补生成失败后没有次数上限，空窗口和坏输出会每小时重复付费（`reports/compose.ts:250-253,352-382`、`schedules.ts:39-48`）；`kinds` 顺序固定为日报、周报、月报且 limit 只计成功数，长期停摆时周/月报被日报积压延迟（`compose.ts:357-367`）；hot_signal 修订只 INSERT 新 `story_signals`，不删除旧故事证据，同一篇文章可在两个事件各计一次热度（`events/group.ts:255,265,491-504`、`events/hot.ts:112-147`）；failed 预筛批次恢复时 `failures` 不重置，下一次错误立即再次 failed（`jobs/prefilter.ts:41-45,219-225`）；归组重试命中 `kept` 分支后跳过 `redirectEmptiedStories`/`reclaimWaiting`/`rematchSignals`（`events/group.ts:270-275,399-429`）；digest 耗尽重试后没有补偿扫描，事件可能长期无综述（`events/derived-content.ts:60-68`、`jobs/events.ts:40-49`）；`content.analyze` 在 short policy 下可在第一个任务仍 active 时再建一个同 article 任务，`analyzeArticle` 无条件 INSERT `analyses` 并再次发布（`jobs/queue.ts:42,149-154`、`editorial/analyze.ts:821-837`，疑似）；`republish-source` 只在成功时写 `done`，失败后进度永久 running（`jobs/publication.ts:16-25`）；`ops.recover` 与 `ops.alerts` 同 cron 但不同队列，没有“恢复先于告警”的顺序保证（`schedules.ts:55-62`）；报告写入不推进 publication epoch，索引缓存最多 60 秒/10 分钟陈旧（`publication/reports.ts:275-292`、`reports/compose.ts:132-156`）。

### 3.18 WEB-01 至 WEB-07：网页与后台交互

**XSS、开放重定向与后台假保护。** 网页分片逐项核对了三处 raw HTML 写入（文章正文、构建期文档、代码高亮）、登录回跳、外部链接和后台 layout 鉴权，未发现可利用的 XSS、开放重定向或“仅隐藏 UI”的后台保护。React 19 会把 `javascript:` href 替换成抛错 URL；后台 layout 在服务端调用 `/api/admin/me`，子页 loader 一律 `adminGet`，无 `clientLoader` 绕过。这是本轮“没有 P0”结论的重要支撑。

**WEB-01（P2）：连接创建不幂等。** `apps/web/app/features/admin/model-connections.tsx:106-111` 创建连接时没有客户端 ID；后端 `providers/model-config.ts:96-98` 用 `id: old?.id ?? randomUUID()`。请求已到达服务端但响应丢失/超时后，前端只显示“网络错误”；再次保存会新建第二个连接。建议提交期间硬禁用，或让前端生成 ID 并作为幂等键。

**WEB-02（P2）：回执计费选择跨回执残留。** `apps/web/app/routes/admin/runs.tsx:25,253,257` 的 `billed` 只在组件挂载时初始化为 `"false"`；为回执 #1 选择“已计费”后关闭，打开回执 #2 仍显示“已计费”。误确认会把未核实状态写入审计并放行重试，后端会重新发起调用。建议关闭对话框时重置所有局部状态，并在提交前要求显式选择。

**WEB-03 至 WEB-07（P2/P3）概述。** 合并事件的目标编号跨对话框残留，非法输入静默失败（`routes/admin/content-item.tsx:45,414-421`）；`/all` 把任何 503 都重定向到“搜索繁忙”，丢失原查询/筛选（`routes/all.tsx:26-28,147-151`）；主题偏好在跨标签、导入、系统主题变化或存储被拒后不应用到页面（`components/shell/ThemeSwitch.tsx:24-25`、`root.tsx:42-43`）；`/agent?tab=foo` 在 loader 规范化后又被客户端 effect 强转，四个分支都不渲染（`routes/agent.tsx:234,288-291`）；对话框缺少焦点陷阱和关闭后焦点恢复，隐藏的“回到顶部”仍在可访问树中，SelectBench 行仅鼠标可点（`features/admin/ui.tsx:300,315-316`、`features/item/PosterSheet.tsx:14-26,45-47`、`components/shell/Chrome.tsx:44-47`）。这些是交互与可访问性问题，不改变公开读取边界。

## 5. 提示词审查与改进

每个功能的完整推荐模板见[提示词模板建议](2026-11-04-提示词模板建议.md)。本节只保留审查结论、改动理由与评测顺序。

### 5.1 当前结构

提示词全部在 `industry/prompts/*.md`，由 `packages/backend/src/editorial/prompts.ts` 装配：`{{name}}` 填值，`{{> file}}` 插入共享规则；缺失值或文件直接报错。版本是文件内容哈希，回执与后台能看到实际使用的版本。单篇与合并路径共用同一套规则，`analyze.ts` 在边界用 zod 校验输出，结构引文还会在实际送入模型的正文里做连续匹配。

本轮用生产装配函数测量了主要 system 提示词的 JavaScript 字符数（不是 token）：

| 提示词 | 字符数 | 说明 |
| --- | ---: | --- |
| `prefilter` | 814 | 单篇预筛 |
| `prefilter-batch` | 1,132 | 批量预筛 system |
| `selection-score` | 4,346 | 单整数输出，最长的 system |
| `structure` | 3,205 | 单项结构 |
| `understand` | 2,990 | 单项内容理解 |
| `understand-structure` | 5,304 | 合并理解+结构 |
| `summarize-structure` | 2,963 | 合并摘要+结构 |

**注意：** 3.9.1 文档记录的 P2a system 为 4,467 字符，当前装配结果是 5,304 字符。差异来自 2026-11-01 的结构 `scope`/`evidence`/`conditions` 改动，不是回归；但“已精简到 4,467”的基线已经过期，后续比较应以当前装配结果为准。

### 5.2 PROMPT-01（P1）：同一份摘要出现两个长度目标

`industry/prompts/summarize-article.md:9` 要求“通常 80-160 字、最多 3 句”；同一请求随后通过 `{{> rules-answer-first-summary}}` 插入 `industry/prompts/rules-answer-first-summary.md:2`，又要求“通常 30–70 字……通常共 2–3 句”。`summarize-long-post.md:7` 同样写 80-160 字并插入同一共享规则。两个范围同时出现在同一条 system/user 消息里；模型只能折中或随机选一个，导致摘要长度不稳定、输出 token 浪费，也让“摘要质量”评测混入长度噪声。

**验证。** 用生产 `promptText('summarize-article', …)` 装配后，结果同时包含 `80-160` 与 `30–70` 两段文字（装配长度 1,756 字符）。这是静态可复现的契约冲突，不需要真实模型。

**建议改法。** 让共享规则只负责结构，不负责数字：“首句直接交代核心主体、动作和结果；其后只补 1–2 项关键细节；通常 2–3 句、一段。” 把数字放回各任务：
- `understand`（`summaryZh`）：30–70 字；
- `summarize-article` / `summarize-long-post`：80–160 字；
- `summarize-structure`：沿用用户消息中的写作模板，不另写范围。

这样只有一个数字来源，改一处不会与另一处打架。

### 5.3 PROMPT-02（P1）：输出契约没有列出 `itemType`/`category` 的合法键

`industry/prompts/understand.md:7` 的输出行是 `{"itemType":"...","authorRole":"principal|observer|relayer",…}`：`authorRole` 给了枚举，`itemType` 只有 `...`。`understand-structure.md:10` 与 `summarize-structure.md:8` 的 `category` 只有 `null`，没有列出 `games|technology|economy|entertainment|ai-models|ai-products|industry|paper|tip|opinion`。`structure.md:13` 只写“字段：category, tags, subjects, scope, fact”，也没有枚举。

代码侧是严格校验：`packages/backend/src/editorial/analyze.ts:169-176` 的 `UnderstandSchema` 用 `z.enum(ITEM_TYPES)`，没有 `.catch`；`CombinedStructureSchema.category` 也是严格枚举。2026-10-27 的真实评测已经记录过一次：模型把中文标签“行业动态”写进 `itemType`，整份结果被 schema 拒绝，付费响应无法消费（见 `docs/系统优化/2026-10-27-提示词精简与全量审查.md:112`）。这不是假想风险。

**建议改法。** 在每个输出行直接写合法键：
- `"itemType":"model_release|product_launch|tool_or_prompt|research_paper|industry_event|opinion_analysis|tutorial_explainer"`
- `"category":"games|technology|economy|entertainment|ai-models|ai-products|industry|paper|tip|opinion|null"`
- `"scope":"single|composite|unknown"`
- `"fact":{"title":"","subject":null,"action":null,"object":null,"occurredAt":null,"evidence":null,"conditions":[]}` 或 `null`

这比在正文里反复解释“用英文键还是中文标签”更短、更确定。

**代码侧兜底。** 在 `UnderstandSchema`/`CombinedStructureSchema` 的边界加一个受控映射：如果 `itemType` 等于 `ITEM_TYPES` 对应的中文标签（或 `category` 等于 `CATEGORIES` 的 `label`），映射为键并记录计数。不要静默接受任意字符串；只接受精确的白名单标签，并在监控里暴露映射次数。这是 `principle-boundary-discipline` 的边界校验，不是把错误藏起来。若映射频繁出现，说明提示词仍在漂移，应回到提示词修正。

### 5.4 PROMPT-03（P2）：`selection-score` 内部有一节“覆盖前文”的规则

`selection-score.md` 长 4,346 字符，只输出一个整数。它在第 109 行又起了一节“事件口径校正”，并明确写“若与前文的直觉判断发生冲突，以本节的事件口径为准”。这会让模型在两层规则之间做优先级判断：一边是“只评事件价值、不评稿件”，另一边是“广泛可用性本身是实质变化”“强事件 + 弱叙事时以强事件为核心”。其中“广泛入口”与 `cred`（证据强度）的边界确实容易冲突，但用“本节覆盖前文”来修补，会让评分稳定性依赖模型对章节顺序的服从。

**建议改法。** 把第 109-117 行的五条校正合并进五轴定义与“品味规则”：例如在 `sig`/`reson` 下直接写“广泛可用性是实质变化；短引用不自动降低事件分；强事件不被弱叙事降格”。删除“以本节为准”的元指令，只保留一套规则。然后用 `scripts/eval-selection.ts` 在冻结样本上做旧/新对照，预先写下通过标准（例如决定性样本准确率不下降、格式失败不增加、总 token 不上升），不要用 5 对样本证明总体提升。

### 5.5 PROMPT-04（P2）：提示词里的“事故疤痕”应改为契约与测试

以下句子都是过去事故的补丁，单独看合理，叠在一起会让提示词变长且互相干扰：
- `prefilter.md:2-3` 先写“只输出JSON”，再写英文“Return only JSON.”；
- `prefilter-batch.md:4-6` 用三段话反复强调 `revision` 必须原样复制、不是数组序号、不能默认填 1；
- `understand-rules.md:13` 写“不增加 answer 字段”；
- `understand-structure.md:11` 写“不要把 structure 嵌入 writing 或平铺其字段”；
- `rules-answer-first-summary` 与各任务模板重复“不要套话开头”。

**建议改法。** 每个输出形状保留一个紧凑契约 + 一个最小合法示例；把“上次模型把中文标签写进 itemType”“把 revision 填成 1”“把 structure 嵌进 writing”变成 `tests/prompt-contract.test.ts` 的断言或解析器用例，而不是继续加句子。这是 `principle-encode-lessons-in-structure`：能编码成检查的，不要再写成提示词。

### 5.6 PROMPT-05（P2）：尺寸基线需要重新测量

3.9.1 的 4,467 字符是当时 `understand-structure` 的 system；2026-11-01 增加 `scope`/`evidence`/`conditions` 后，当前装配是 5,304 字符。字符数不是 token 数，中文与英文的 token 比例也不同；不能用“system 字符减少 52%”推断总 token 同幅下降。建议在测试里记录每个 prompt 的装配字符数，并在回执里按步骤汇总实际输入+输出 token；优化收益只看总 token，未知用量单列。

### 5.7 PROMPT-06（P3）：合并摘要的 system 不自包含

`summarize-structure.md` 的第一行说“用户消息中的写作、事实、专名与条件约束适用于全部字段”，但 system 本身只包含结构规则与标签；写作规则、安全规则、领域规则都在用户消息里。`analyze.ts:589-591` 还给 `promptText("summarize-structure", …)` 传了 `writingRules`，但模板没有引用它。当前调用方 `runCombined` 总会构造带写作规则的 user 消息，所以行为正确；但这是一个隐式依赖：未来新增调用方若只渲染 system，就会丢掉安全与写作约束。

**建议。** 要么在 `summarize-structure.md` 中显式插入 `{{writingRules}}` 与 `{{> safety}}`，要么在 `promptText` 调用处删掉未使用的参数并在测试中断言“合并摘要的 user 消息必须包含写作规则”。两者选一，不要保留“传了但没用”的状态。

### 5.8 提示词改进的执行顺序

1. **先改契约，不改风格**：PROMPT-02 的枚举键、PROMPT-01 的长度单一来源。这两项风险低、可静态验收。
2. **加边界兜底**：中文标签→键的白名单映射 + 计数；只记录，不扩大接受范围。
3. **再加测试**：装配每个 prompt，断言无未解析 token、输出行包含 schema 枚举、同一装配结果不出现两个冲突的 `\d+[-–]\d+字` 范围，并记录字符数。
4. **最后动评分提示词**：PROMPT-03 的合并需要真实评测，按 `docs/内容管理/精选评分与校准.md` 的冻结样本与固定种子流程跑；预先写通过标准，不把有限样本写成总体质量证明。
5. **观察**：改动后按自然日看格式拒绝率、`itemType` 映射次数、摘要长度分布、每篇总 token；未知用量单列。
