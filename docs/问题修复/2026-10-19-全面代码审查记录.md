### R07：分析提交只核对正文版本，没有核对重评轮次

**触发与影响：** 同一文章正文 revision 未变，旧分析仍在运行时管理员发起重评；新轮次先完成，旧轮次后提交。旧结果被认定 `stale=false`，发布层选择同 revision 下 id 最大的分析，公开标题等字段重新变成旧轮次结果。它会违背人工重评意图，但不是人工 `editorial_overrides` 字段被覆盖。

**代码证据：** [admin/content.ts](../../packages/backend/src/admin/content.ts) `rerun`（163 行起）及 [jobs/content.ts](../../packages/backend/src/jobs/content.ts) `queueProcessing`（71 行起）写入 `processing_attempt_tag`，人工任务使用独立 singleton key；[editorial/analyze.ts](../../packages/backend/src/editorial/analyze.ts) 634—647 行只比较 `revision`；[publication/publish.ts](../../packages/backend/src/publication/publish.ts) 189—191 行按 `input_revision DESC, id DESC` 选分析。worker 的 `processRevision` 对 `stale=false` 继续发布。

**复现：** 本地替身完成旧轮次请求，仅在真实 `INSERT INTO analyses` 事务开始前暂停调度；调用 `rerun` 并完成新轮次；恢复旧轮次。读回公开标题为“旧轮次合成标题”。没有伪造 SQL 结果或付费回执。该探针直接驱动业务函数，没有用真实 worker 的随机延迟寻找竞争窗口。

**建议与验收：** 引入可持久核对的分析代次／轮次，提交及公开选择同时核对，不能只把旧结果标 stale 后仍允许发布层选中。保留旧轮次审计和已付费回执；覆盖旧→新、新→旧两种完成顺序、正文变更、重启恢复和同一 requestId 重试。

### R08：综述预算等待被当作普通失败消耗重试

**触发与影响：** 需要模型生成的综述遇到持续预算限制，超过首次执行加 3 次重试后任务进入 `failed`。预算恢复本身不会再安排该综述；后续相关报道、纠错或人工操作可能重新触发，所以不能称为绝对永久失败。

**代码证据：** [jobs/events.ts](../../packages/backend/src/jobs/events.ts) `processGroupingJob` 对等待调用 `requestWait`／`deferJob`，而 `registerEventJobs` 的 digest handler 直接调用 `composeStoryDigest`；[jobs/queue.ts](../../packages/backend/src/jobs/queue.ts) 50 行配置 digest `retryLimit:3`、60 秒退避，`retryReleasedReceiptJobs` 仅匹配回执释放审计；[operations/recover.ts](../../packages/backend/src/operations/recover.ts) `recoverStaleWork` 未补扫预算失败的 digest。[worker/schedules.ts](../../apps/worker/src/schedules.ts) 的 `stories.status` 只更新事件状态，不补做综述。

**复现：** 创建两篇可公开合成报道和事件，将替身供应商预算置 0；用真实 pg-boss 队列策略 fetch／fail 四次，`ignoreStartAfter` 仅跳过等待时间。每次业务调用抛 `BudgetExceededError`，最终 `failed`；恢复预算并调用 `recoverStaleWork`，可领取任务为 0、综述仍空、本地供应商请求数 0；显式调用 `composeStoryDigest` 后成功且请求数为 1。未模拟 wall-clock 调度或真实账号窗口。

**建议与验收：** 综述采用与归组一致的等待策略，保留 `storyId` 对应 singleton、剩余真实失败额度和关机语义；另处理已经失败的历史任务。不要不加区分地重排全部失败任务，避免未知回执被重复购买。覆盖预算／忙碌／关机等待、恢复后补做及 receipt unknown 的独立流程。

### R09：静态目录校验只比较字符串前缀

**代码证据：** [apps/web/server.ts](../../apps/web/server.ts) `serveStatic` 47—60 行在解码前检查 `..`，解码后 `path.join`，只用 `file.startsWith(CLIENT_DIR)` 限制路径。

**复现：** 仅在隔离检查容器创建 `apps/web/build/client-review-fixture/probe.txt` 哨兵文件。使用 Node `http.request` 保留原始路径，请求 `/%2e%2e/client-review-fixture/probe.txt`，实际返回 HTTP 200 和哨兵内容。浏览器或某些 URL 客户端可能先规范化路径，不能用它们未成功就否认此边界问题。

**影响边界：** 已证明静态根目录之外、名称共享 `client` 前缀的兄弟目录可读；**未证明可以读取任意文件、`.env` 或当前生产凭据**。实际泄露取决于这类目录是否存在可读文件，本次没有在生产布置探针或枚举敏感目录。

**建议与验收：** 解码后用明确的目录边界检查，例如 `path.relative` 后拒绝父目录与绝对路径；明确符号链接的部署约束。覆盖编码斜线／父目录、同前缀兄弟目录、合法中文文件名和合法静态资产。

### R06：连接删除未检查能力引用

**代码证据：** [providers/model-config.ts](../../packages/backend/src/providers/model-config.ts) `deleteModelConnection` 124—132 行仅拒绝删除 active 默认连接；[editorial/models.ts](../../packages/backend/src/editorial/models.ts) 34—52 行过滤不存在的注册模型，随后回退环境／默认值。能力配置在数据库 `settings`，连接在私有配置文件。后台 [model-connections.tsx](../../apps/web/app/features/admin/model-connections.tsx) 177 行删除按钮仅因 pending／active 禁用，直接发 DELETE，未显示受影响能力清单。

**复现：** 新建非默认合成连接，令 `models.score` 指向它，确认 `modelFor('score')` 返回该连接；删除成功后 settings 仍保留旧引用，但解析结果换成环境／默认模型。

**影响与建议：** 后续请求可能改变模型、供应商或推理配置；未证明一定增费，也未证明生产发生过。删除前列出并阻止未处理的引用，或要求显式迁移能力；并发删除／能力修改需同样保护。缺失配置可有可用性回退，但应能被观察和审计，不能只靠页面显示删除成功。

### R04：模型输入身份遗漏媒体与引用帖变更

**代码证据：** [content/materials.ts](../../packages/backend/src/content/materials.ts) `contentHash` 仅包括标题／正文／摘要；181—182 行同 hash 直接返回，媒体及 `x_post` 更新在 213 行之后。[editorial/input.ts](../../packages/backend/src/editorial/input.ts) 89、108 行实际把引用帖和图片送入理解路径；评分输入也读取引用文本。

**复现：** 同一材料正文不变，仅将首图 URL 与 `xPost.quoted.text` 改为新值，`revised=false`，数据库媒体及引用仍为旧值。

**影响与建议：** 上游更正图片或引用信息时，后续展示和分析可能继续使用旧输入。应区分“会改变模型事实依据的字段”与普通元数据，再决定更新及推进 revision 的范围，避免图片 URL 临时参数刷新导致无意义重评。复现是材料入口调用，未证明现有每一种采集器都会产生此类更新；当前生产仅启用 RSS，引用帖影响属于支持能力的边界。

### R02：评分强制转换掩盖无效模型输出

**代码证据：** [editorial/analyze.ts](../../packages/backend/src/editorial/analyze.ts) 79 行 `ScoreSchema` 使用 `z.coerce.number().int().min(0).max(100)`；两次评分调用共用该 schema。

**复现：** `attentionScore` 分别为 `null`、空字符串、`false`、`true`、空数组和空格时，实际校验全部成功，值为 0 或 1。

**影响与建议：** 格式错误会被当成真实低分，影响精选及后续理解／摘要分流，且不会走无效输出恢复。应严格接受数值；若需要兼容数字字符串，应限定语法，拒绝 null／布尔／数组／空白。未统计真实模型出现这些值的频率；不要据此重新购买所有历史评分。

### R01：反馈截图共享路径却按单条记录删除

**代码证据：** [operations/feedback.ts](../../packages/backend/src/operations/feedback.ts) 66—70 行用内容 hash 和扩展名命名文件；[admin/feedback.ts](../../packages/backend/src/admin/feedback.ts) `eraseFeedback` 直接 unlink，没有检查其他记录引用。[notify/feishu.ts](../../packages/backend/src/notify/feishu.ts) `screenshotFor` 上传成功／放弃也直接 unlink，存在相同引用风险；飞书分支本轮只做静态核验。

**复现：** 两条反馈提交相同截图字节，得到相同文件路径；删除第一条后第二条仍保留 `screenshot_key`，但文件已不存在。

**影响与建议：** 另一条反馈的附件丢失。可按反馈分配独立文件，也可实施显式引用管理，删除和并发上传必须一起考虑。生产观察时反馈总数为 0，不能声称已经丢失真实截图。

### R10：网页代理未传播客户端断开

**代码证据：** [apps/web/server.ts](../../apps/web/server.ts) `isApiOwned` 代理分支只注册 upstream `error`，没有将客户端响应关闭／请求中断传播给上游，也没有该分支显式总超时。

**复现：** 本地假 API 接收请求后保持响应打开；客户端销毁连接，等待 1500ms，上游响应连接仍未关闭。测试结束主动销毁连接并退出子进程。

**影响与建议：** 慢请求或异常后端下可能积累无用连接／工作；本次没有压测，未证明生产已资源泄漏，也没有证明连接永不被基础设施超时回收。应在下游断开时终止对应上游请求，并为适用接口设置超时及完成后的监听清理。对 SSE 等长连接需独立策略，不能简单给全部 API 加短超时。

## 4. 已核实的设计边界，不冒充未声明 bug

### R03：真实回滚与采集防抖无法区分

[content/materials.ts](../../packages/backend/src/content/materials.ts) 202—208 行对任意历史 hash 直接返回；注释明确认为真实回滚少见，[tests/materials.test.ts](../../tests/materials.test.ts) 148 行起也明确要求返回旧版本不产生新修订。因此这是一项**既有策略的业务代价**。

合成复现：A“尚未宣布上线”→B“已经宣布上线”→有更晚 `sourceUpdatedAt` 的 A，最终正文仍 B、revision 仍为 2。防抖避免循环分析和无效付费，但真实撤回／纠错可能长期保留相反事实。建议先定义可信更新时间、来源类型和定向纠错规则，再处理真实回滚；不建议直接删除全部防抖逻辑。本轮未证明生产存在此类案例。

### R05：清除人工覆盖和清空公开文字是两种需求

[admin/content.ts](../../packages/backend/src/admin/content.ts) 126—150 行允许 `summary:''`／`reason:''` 存入覆盖；[publication/publish.ts](../../packages/backend/src/publication/publish.ts) `pickString` 会将空白回退到模型文字。探针确认空覆盖存在但公开摘要／理由仍为原文。

进一步核对 [后台内容表单](../../apps/web/app/routes/admin/content-item.tsx) 333—342 行后，确认 UI 明确说明“留空表示不修正”，并将既有字段的留空转换成 `clear`。因此**不把 UI 留空后出现模型文字判为保存失败**。当前确实缺少“保持该条内容公开，但明确不显示摘要／推荐理由”的表达方式；是否需要它属于产品决策。低优先建议是 API 拒绝／规范化空白覆盖，使存储与有效语义一致；若新增显式空值，需与 `clear` 恢复模型默认值区分。

## 5. 复杂度与维护建议

以下是维护判断，未测量重构后的性能或成本，也不构成本轮修改授权。

1. **等待／失败／未知回执策略分散。** 文章、归组、综述、队列重试和恢复扫描各自承担部分状态，R08 已显示遗漏后果。优先提取小范围的等待分类和重排契约，保留不同业务 singleton／回执语义，不重写整个任务系统。
2. **Token 有效性规则存在多份实现。** [providers/model-usage.ts](../../packages/backend/src/providers/model-usage.ts) 的 `normalizeModelUsage`、[admin/model-stats.ts](../../packages/backend/src/admin/model-stats.ts) 43—80 行 SQL 的 safeTokens／raw／checked，以及 [admin/model-costs.ts](../../packages/backend/src/admin/model-costs.ts) 的缓存状态兼容表达式需要同步。当前未复现统计差异；建议共享边界样本和契约测试，不为复用而把大规模 SQL 聚合搬回 JS。
3. **分析编排职责集中。** [editorial/analyze.ts](../../packages/backend/src/editorial/analyze.ts) 同时处理提示词版本、独立与合并请求、旧回执恢复、输出归一化、发布输入写入，理解成本较高。后续修改时可优先拆纯输入构造／归一化；收费身份、互斥和提交顺序不应为了缩短文件而重排。
4. **连接和能力分属两种持久化介质。** 私有文件连接配置与数据库 settings 之间没有直接引用完整性约束，R06 暴露了删除时遗漏。先补服务层引用校验和可观察性，再评估是否值得迁移存储；不需要为了架构“整齐”把密钥搬入普通配置表。

回执、预算熔断、公开投影、两次评分、独立优化开关和历史增量迁移都有明确的业务或安全用途，本轮没有证据支持把它们当成冗余删除。也不以较长文件、SQL 行数或历史兼容代码的存在单独判定过度设计。
