## 2026-10-15 PR #7 队列领取轮次补修

审核意见成立：`deferJob` 仅按任务 ID 和 active 锁行，会结算同 ID 已重新领取的轮次。worker 现在读取元数据并传递领取时的 `retryCount`，归组处理继续传入延迟事务；事务在行锁内同时匹配名称、ID、active 与该 retryCount，结算时也传递 `{ id, retryCount }`。不属于当前领取轮次时，不完成任务、不插入或修改延迟后继。既有后继插入故障回滚、较新载荷、等待时间、优先级及剩余真实失败额度继续回归。

源码核对还发现原锁定依赖 pg-boss `12.34.0` 不支持审核引用的 JobAttempt API，且 worker 的自动 complete／fail 仅按 ID 执行。真实 worker 的三项复现证明：只补本地 SQL 校验后，旧处理器正常返回、抛错或进入延迟路径，仍会由库的自动结算影响已重新领取的任务。因此升级至最小支持版本 **12.35.0**，利用库本身对自动结算的领取轮次保护；没有直接修改依赖源码。npm 对锁文件的无关排序和平台 libc 元数据调整已排除，仅保留 pg-boss 的版本、归档地址、完整性及工作区依赖版本变化，传递依赖版本不变。

新增六项真实数据库／worker 回归：陈旧延迟不能完成新领取者或修改其后继、当前领取者仍可延迟且不恢复已用失败额度、真实 worker 传递捕获的轮次、旧处理器正常返回／抛错／延迟时自动结算均不得改变新领取者及后继。修复前前两项出现 `Missing expected rejection`、适配器未传 retryCount；本地 SQL 修复后但依赖仍为 12.34 时，三项真实 worker 复现全部失败。依赖与调用链修复后相关 **18/18 通过，失败、取消、跳过 0，1.668 秒**，完整类型与版本同步通过。早期 worker 夹具沿用 20 秒指数重试等待，后改为夹具自身 retryDelay=0、retryBackoff=false，以直接测试领取轮次；生产重试设置和断言未变。

该依赖升级包含内部队列 **schema 42→43**，增加统计与死信溯源字段及索引，并非“没有数据库变更”。在独立新库使用实际 12.34 包建立 schema 42，保存 created／active／retry／failed 四种任务，再由实际 12.35 包启动升级：任务数量、ID、载荷、优先级、重试次数与上限、单例键、起止时间及输出逐一不变；错误轮次 complete 影响 0 行，正确轮次影响 1 行。停下新运行库后，实际旧 12.34 包可在 schema 43 接续并完成原待执行任务，不回退结构或恢复旧数据库；此项只验证队列运行库的兼容性，不替代整套旧应用回退验收。生产升级须按[手动部署](manual-deploy.md)另行取得具体授权，本次未访问或改变生产。

`useModelStubs` 只接受本测试进程由 `stub()` 创建且尚未关闭的服务，写入虚构的测试密钥，并临时开启内存中的模型入口；环境变量开关仍为 false。这样可以验证评分、回执、预算、归组与恢复流程，不调用真实模型。关闭安全阀的用例仍验证请求在发送前被拒绝。独立子进程测试必须显式指向本地替身，并在隔离网络内运行。

## 共享数据库与断言

整个套件按文件串行运行，因为用例共享预算及队列。文件之间的行即使有唯一标签，也可能被全库恢复扫描选中；涉及扫描时应检查本用例文章的完整任务集合及重复执行的稳定性，不能把全库返回数量当成本信源的数量。使用真实队列 worker 的用例要临时停放其他用例的任务，结束后恢复。

缓存前后的评分、决策、覆盖率和已记录 token 应相等；墙钟耗时分别验证为有限非负数。缓存会改变耗时，不能要求首次计算与缓存复用耗时相等，也不强制要求每次缓存调用都更快。
