## 1. 目标与范围

优先减少重复请求和同一材料的重复输入，在保持新闻覆盖、精选标准和公开内容质量的前提下降低用量。第一阶段推荐实施：**单篇事件复用已有摘要、合并结构抽取与写作**；之后按测量结果决定是否推进综述刷新合并和批量预筛。

主要衡量同一连接、型号及 effort 下，每篇完成处理文章的实际请求数、非缓存输入、缓存输入和输出 token，同时检查事件综述生成次数、失败重试和处理延迟。未知用量单列，不能算作零；推理 token 已包含在输出内，不再次相加。

本计划保留以下边界：

- 当前账号、`gpt-6-luna`、管理员选择的 effort、连接复用、两项并发上限 2、站内预算和生产开关。使用者已独立将预筛、普通摘要、结构抽取调整为 low，本实现不再更改这些选择。
- 五个兴趣领域、既有信源、两次独立评分、五维评分结构、信源分级门槛与宽召回预筛规则。不能直接把两次评分改成一次，也不能让一次回答伪装成两次独立判断。
- 所有付费请求继续经过回执与预算；在途、未知结果、共享消费者和有限恢复保护继续有效。新用途或新提示词不能绕过旧请求的未知状态。
- 模型只由 worker 调用；公开出口继续走统一发布读取层，页面访问不触发推理。许可撤回和人工修正继续及时生效。
- 优化自然作用于后续工作，不批量重评历史文章或重写历史事件。数据库变更、发布及应用回退按[手动部署](../运维部署/生产环境手动部署.md)执行，回退不恢复旧数据库或删除付费回执。

346 条单篇综述关联的回执用量为输入 **1,920,131**、缓存输入 **1,170,048**、输出 **47,759**，覆盖当时实际使用的连接；不能全部计为 Codex 消耗。500 条已保存综述属于 401 个事件，60 个事件当天生成多次，单个事件最多 9 次。单篇复用和多篇刷新合并的收益可能重叠，不能直接相加。

模型请求按 `receipt_attempts.started_at`、`origin='live'` 且型号非空统计；重试按实际 attempt 计数。已保存综述按 `story_digests` 所引用回执的 `created_at` 落入窗口统计，单篇指 `cardinality(article_ids)=1`。二者统计对象不同，不能把“少生成一条综述”等同于精确少一次付费请求。

### 2.3 复查方法

通过 NAS 的 `deploy/nas/compose.sh exec -T api node --input-type=module`，调用 `modelsOverview()` 获取现有汇总；默认是最近七天，传入 `1` 表示滚动 24 小时，均不等于北京时间今天。具体入口见[维护说明中的只读统计](../运维部署/站点维护说明.md#首轮预算和用量)。

比较固定窗口时，在只读事务中按上述 UTC 起止时间查询 attempts，按连接、请求型号、用途及已保存的 effort 分组；新记录优先采用 `normalized_usage`，旧记录复用后台现有的安全解析规则，缺失缓存明细保持未知。日报窗口与滚动预算窗口分开统计。

只输出汇总，不导出原始响应、环境文件、密钥或授权文件。需要核对模型默认值时使用应用提供的 `model/list` 与经过字段筛选的 `config/read`，不发起测试推理。

## 3. 实施顺序

| 阶段 | 交付 | 完成后再决定的事项 |
| --- | --- | --- |
| P0 | 固定比较样本和统计口径 | 确认质量基线、材料分布及当前默认配置 |
| P1 | 单篇事件复用已有标题、摘要 | 用实际命中率和用量判断收益 |
| P2a | 同一有效模型配置下合并内容理解与结构 | 独立开关；检查结构完整性、恢复、请求数和延迟 |
| P2b | 在 P2a 回归通过后合并普通摘要与结构 | 独立开关；覆盖原文本摘要、帖子和身份校验 |
| P3 | 合并多篇事件的短时间刷新 | 根据新鲜度要求确定等待窗口 |
| P4 | 按 token 上限批量预筛 | 先解决逐篇恢复及未知回执边界 |
| 后续 | 材料清理、提示词与 effort 评估 | 只有前述阶段仍有明确瓶颈时再扩展 |

每项单独实现、验证并记录收益，避免同时改变流程和模型导致结果无法归因。第一阶段不承诺固定节省百分比；已观测的历史用量只能作为机会规模。

## 4. 第一阶段设计

### P0：建立可比较的基线

- 按五个领域、中英文、长短正文、精选与非精选、单篇与多篇事件固定一组材料，保留输入修订号、许可范围和原有结果。精选难例沿用[标注与校准方法](../内容管理/精选评分与校准.md)，综述沿用[现有评测工具](../内容管理/事件综述评测.md)。
- 将全量请求总数与每篇完成文章的平均用量一起比较，记录失败／未知及缺少用量的覆盖范围；对事件另外统计每次新增报道带来的综述生成次数，不能只看 token 总量或缓存命中率。
- 性能与恢复回归使用隔离库和本地模型替身；真实内容质量比较如需新模型结果，另行明确样本、环境、最大付费 attempts 与预算。现有评测的案例数上限不能当作包含所有重试的付费次数上限。
- 固定合成材料覆盖五个领域、中英文、长短文本及精选／非精选，逐项断言原文事实、主体、分类和两次独立评分；记录实际 attempts、回执复用与延迟。替身结果只证明流程与计数，不证明真实模型质量或生产节省比例。

### P1：单篇事件复用已有摘要

涉及[事件综述生成](../../packages/backend/src/events/digest.ts)、[输入依赖与撤回](../../packages/backend/src/events/derived-content.ts)、发布读取层和对应回归。

1. 按 `digestReports()` 的当前许可和内容条件读取报道；只有一篇且已有可用摘要时，用其已发布的中文标题、摘要形成事件概览，不再调用模型。人工事件标题继续保留；素材不足时沿用现有等待或生成规则，不从标题补造事实。
2. 在 worker 的写入路径保存确定性结果、完整文章依赖、输入 hash 及版本，保留提交前的版本和权限复查。已有 `story_digests.receipt_id` 可空；复用路径不伪造付费回执，不把文章原回执再次计为事件模型请求。
3. 相同输入重复任务直接复用。单篇来源被修正、撤回、移出或合并时，继续使用现有失效与恢复路径；不能仅根据“仍是一篇”复用旧内容。
4. 出现第二篇有效报道后，回到多篇综述生成。若原单篇摘要仍有完整有效依赖，可作为已验证的上一版输入；否则按当前材料完整重建。
5. 第一轮仅影响后续新建或自然更新的事件；遇到已有模型稿且输入未变时保持现有稿，不批量替换历史综述。

验收重点：满足复用条件的单篇事件新增付费 attempts 为 0；第二篇报道、人工标题、修正、撤回、并发版本变化与重复任务均正确。网页、RSS、API、MCP 的新响应遵守同一许可边界；依赖撤回不等待下一次模型调用。

### P2a／P2b：分步合并结构抽取与写作

涉及[文章分析流程](../../packages/backend/src/editorial/analyze.ts)、[材料输入](../../packages/backend/src/editorial/input.ts)、[写作与身份校验](../../packages/backend/src/editorial/writing.ts)、[行业提示词](../../industry/prompts)及相关回执统计。

1. 两次评分保持独立，完成后按原规则选择内容理解或简短摘要。让相应写作请求同时返回分类、标签、主体和事实，减少独立的结构请求；不把评分输出或结构结果反向混入独立评分输入。
2. 默认要求结构与写作的有效连接、型号、effort 及输入能力一致。P2a 另允许同一全局 Codex 账号下、同型号及相同输入能力的结构 low 与理解默认／medium 配置合并，整次请求沿用理解配置；不修改后台分配、连接或强度。API Key 连接、不同供应商归属、型号、输入能力或其他强度组合仍分开；P2b 继续严格比较完整配置。中文短帖等本来无需模型写作的情况也保留单项结构抽取。
3. 保留结构字段白名单、事实约束、文案格式、主体身份校验和图片失败的原处理边界。统一输入覆盖两项任务真正需要的材料，先清理重复内容，不直接把完整材料改成摘要评分。
4. 升级过渡时，旧结构或写作请求有在途／未知结果的，先沿旧恢复规则等待；已有单项结果的复用原结果，缺失项继续原单项路径。仅两项均未开始的新处理进入合并路径，避免新增用途绕过旧付费保护。
5. 合并请求只登记一个真实 attempt，结果供两个阶段使用；能力统计不能重复累计。新增用途需要同步接入后台汇总和诊断，不能因查询漏掉新用途而制造用量下降。
6. 保留结构与写作的原子校验边界；解析失败按原回执规则有限重试，不自动重新拆成两次付费调用。禁用合并后，已接收／未知的合并请求仍按原路径消费或等待。

实施补充（2026-10-17 代码审查）：

- P2a、P2b 分别开关，默认关闭；只有兼容配置且本轮结构与写作均未开始时才进入。真实质量评测及生产自然增量尚未完成时，只交付可验证的候选实现，不宣称生产收益已经验收。
- 合并结果分成独立的 `writing` 与 `structure` 对象，区分两项任务的标签。结构必需字段缺失或类型错误必须拒绝整份结果，不能因旧 schema 的 `catch(null)`／空数组容错静默接受；业务允许的无事实仍可显式返回 null。
- 同文章修订、同处理轮次的单项／合并请求互斥，跨用途保护在付费占位事务中完成，覆盖并发切换；旧回执及其共享消费者参与判断。已开始的路径由回执持续标识，失败或关闭开关不自动拆分重发。
- 新用途必须登记未知回执放行与文章恢复，同时核对总量和能力统计；一个合并回执只累计一次，文章回执列表去重。
- 本地复用同时检查提示词版本和材料指纹，覆盖文章修订号未变但信源元数据或已有译文改变的情况；升级前未保存材料指纹的单项回执，按原 user hash 核验，不仅按文章 ID／修订号复用。
- 收到的合并结果在开关关闭或模型分配变化后仍可本地校验、消费；未知结果继续等待，释放后的有限重试沿原路径。应用回退必须使用能识别合并回执的兼容版本，不能直接假定旧 3.5.2 worker 可以安全消费。
- 缺图、图片拒绝、内容过滤和中文短帖保留原有边界。P2b 必须单独覆盖原文本输出向合并 JSON 输出的变化。
- 明确的内容过滤拒绝保留原摘要降级，此例外不能用于解析失败、在途或未知结果；重复任务复用已收到的降级文案，不反复尝试被拒绝的理解请求。

当前结构抽取与评分并行，合并后写作需要等待评分，因此必须比较端到端延迟。验收包括精选决策、分类／标签／事实正确性、中文文案、缺图降级、部分历史结果复用、模型分配不兼容、回执恢复和统计去重；验证既有最长三分钟公开门槛继续生效。

三分钟从文章达到精选发布条件后计算，不是采集到公开的总耗时上限。分别记录分析耗时、采集到公开耗时与报道到综述更新耗时，不能以公开门槛未变代替端到端时效验证。

## 5. 后续候选

### P3：合并多篇事件的连续刷新

当前[归组任务](../../packages/backend/src/jobs/events.ts)在入队时设置 `startAfter: 60`，并使用同事件 singleton key；这能减少部分重复任务，不等于持续推迟的完整防抖。

- 候选方案是普通新增报道在约五分钟内合并更新，并设置从首次待更新起计算的最长等待时间，避免报道持续到来时永远不生成。五分钟仅为试验起点，最终以新鲜度和实测收益决定。
- 任务真正执行时重读当前输入，不依赖首次入队快照；保持同事件的幂等与版本校验，不对每篇新报道分别强制生成。
- 人工修正、权限撤回先同步失效公开文字，再走优先恢复路径，不套用普通延迟。已归组文章的公开时间轴和最长三分钟门槛不依赖综述刷新完成。
- 验证重启、多个生产者、预算等待、合并与撤回时不丢任务；记录新增报道至可用综述的延迟，不只统计调用减少量。

### P4：批量预筛

按兼容模型配置和材料 token 上限组成小批，初始候选为每批 5—10 篇、最长等待约 30 秒；长文或低流量时允许小批／单篇。满批十篇由十次请求变为一次，但不能据此承诺生产中预筛请求必减九成。

- 保持宽召回、素材不足为 UNKNOWN 等原语义，每篇使用固定标识和修订号，输出逐篇校验；遗漏、重复、错配结果不能当作 BLOCK。
- 在付费之前持久化不可变的批次成员、顺序、输入版本和配置，批次一个真实回执，逐篇登记消费者；重启后先恢复原批次，不重新组批绕过未知状态。
- 批次结果完整收到后，分别校验和提交各文章；过期修订不能覆盖新修订，单篇提交失败不重复发送整批。结果缺失、解析失败与修订变化的处理需要先明确有限重试及放行规则，禁止无限拆批重发。
- 预算按真实批次请求计数，不伪装成逐篇已付费请求；组批必须另有单批输入上限，避免请求次数下降但单次材料无限增大。
- 当前预算按请求次数限制，不是 token 配额；批量化前必须量化相同次数预算承载的 token 增幅。Codex 未发送 `maxTokens` 生成上限，不能以该参数替代实际输入上限和结果检查。

该项恢复复杂度高于前两项，先验证崩溃恢复、共享回执放行、部分结果和文章间干扰，再决定是否上线。需要持久化新结构时，先设计向后兼容迁移并按手动部署规则处理。

### 材料、提示词和 effort

- 对重复段落、页尾推荐和明确无关的页面残留做确定性清理；保留主体、数字、日期、适用条件、否定和冲突信息，不额外调用模型来压缩每篇输入。
- 预筛可评估先读标题与 RSS 摘要，不足以判断时沿原流程读取更多材料；评分继续依据完整材料，不能把预筛结果或截断后的缺失信息当作排除依据。
- 稳定公共提示词前缀，减少重复列举和格式冗余；复用连接继续保持文章会话独立，不为省 token 把不同文章塞进同一累积会话。缓存命中仍以供应方返回为准。
- 简单预筛和结构任务可用固定样本比较 `low` 与当前默认强度，先看误拦、字段错误和重试变化。降低 effort 不会消除输入开销，不能根据档位预估整体节省比例。
- 当前 Codex 适配器未把 `maxTokens` 作为生成上限发送，不能仅调小调用方数值就声称减少输出。若将来调整参数支持，应以协议实际能力和回归结果为依据。
